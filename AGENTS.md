# pmo-docs

A project-office and documentation workflow packaged as an Agent Skill (`skills/pmo-docs/`). Plan, decisions and checklist: `docs/PLAN.md`. Read it before changing anything structural. Use the words in `GLOSSARY.md`.

## Rules
- **Never commit or push without the maintainer's approval.** Never add `Co-Authored-By`, "Generated with Claude Code" or any attribution line to commits or PRs.
- **No private data in this repo.** No real names, roster slugs, emails, phone numbers, machine paths or client/project names from the source project. The repo is public. Enable the commit gate once per clone: `git config core.hooksPath .githooks` (pre-commit runs `dev/scrub.sh`, commit-msg checks the subject). Never use `--no-verify`. The names it checks live in the untracked `.scrub-names`.
- Fresh history only. Copy source files into `tmp/source/` (gitignored, inside this repo) and stage only generalised files; never import the source project's git history.
- Generic by default: anything project-specific comes from the user's `pmo/config.yaml`, never from the code or templates.
- `skills/pmo-docs/` must work alone (other agents load only the skill folder). `SKILL.md` uses only open Agent Skills fields (`name`, `description` up to 1024 chars, `license`, `compatibility`, `metadata`, `allowed-tools`). The folder name equals `name`.
- Behaviour rules live only in `SKILL.md`. Other files link to it.
- Dependencies: PyYAML only, vendored in `skills/pmo-docs/scripts/_vendor/` (pure Python, `safe_load` only), so users install nothing. No new dependency without asking.
- Tests live in `tests/` and run on the one fake project, `examples/acme`, copied into a temp folder: `python3 -m unittest discover tests`. No network, no real data, nothing written outside a temp folder. CI runs them on every push.
- Python 3.10+, Linux and macOS (Windows through WSL): stdlib plus the vendored PyYAML, every script stops with a clear message below 3.10, answers `--help`, and reads and writes files as UTF-8.
- When a term changes, update `GLOSSARY.md` in the same change.

## Commits and changelog
- `CHANGELOG.md` is generated by git-cliff from commit messages (`cliff.toml`). Never edit it by hand.
- Prefer conventional commit subjects (`feat: ...`, `fix: ...`, `docs: ...`, `chore: ...`), one line, no body. Non-conventional commits are kept (under "Changed"); `chore`, `ci`, `test`, `style`, `build`, `refactor` and `docs(plan|dev|memory)` are left out of the changelog. The subject is the changelog line, so keep it readable and free of private names (`dev/scrub.sh` checks messages too). Breaking changes use `feat!:` or `fix!:`; bumping `schema_version` or renaming a config key or a template section is breaking.
- `CHANGELOG.md` is first committed by the v0.1.0 release; until then it is not committed.
- To release: `dev/release` (planned, Phase F). Until it exists: `git-cliff -o CHANGELOG.md --tag vX.Y.Z`, commit as `chore(release): vX.Y.Z`, then tag. `git-cliff --bumped-version` suggests the next version.

## Layout
```
skills/pmo-docs/   the skill: SKILL.md, references/, assets/, scripts/
.claude-plugin/    plugin manifest (planned, v0.1)
examples/acme/     the fake project used by tests and the walkthrough (planned)
tests/             tests
dev/               maintainer tools (scrub), not shipped to users
docs/PLAN.md       the plan
memory.md          project state for the next session (local, never committed)
```

## Session start
Read `memory.md`. When the user says **wrap-up**, update it with new rules (and why), state and open threads (absolute dates). Leave out what code or git history already hold.

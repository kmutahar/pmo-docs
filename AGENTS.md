# pmo-docs

A project-office and documentation workflow packaged as an Agent Skill (`skills/pmo-docs/`). Plan hub and settled decisions: `docs/PLAN.md`; each version's plan: `docs/plans/`. Read the hub before changing anything structural. Use the words in `GLOSSARY.md`.

## Rules
- **Never commit or push without the maintainer's approval.** Never add `Co-Authored-By`, "Generated with Claude Code" or any attribution line to commits or PRs.
- **Never stage files.** The maintainer reviews edits and stages them. Never run `git add`, `git restore --staged` or `git rm --cached`. When asked to commit, use `git commit -- <paths>` (tracked files only; for a new file the maintainer runs `git add` first). Commit in chunks that follow the plan's task order, one subject per chunk, and propose the chunks first. Never commit `memory.md`, and `docs/PLAN.md` only when told. Check `git status` before and after: staged state changes outside your session.
- **No private data in this repo.** No real names, roster slugs, emails, phone numbers, machine paths or client/project names from the source project. The repo is public. Enable the commit gate once per clone: `git config core.hooksPath .githooks` (pre-commit runs `dev/scrub.sh`, commit-msg checks the subject). Never use `--no-verify`. The names it checks live in the untracked `.scrub-names`.
- Fresh history only. Copy source files into `tmp/source/` (gitignored, inside this repo) and stage only generalised files; never import the source project's git history.
- Generic by default: anything project-specific comes from the user's `pmo/config.yaml`, never from the code or templates.
- `skills/pmo-docs/` must work alone (other agents load only the skill folder). `SKILL.md` uses only open Agent Skills fields (`name`, `description` up to 1024 chars, `license`, `compatibility`, `metadata`, `allowed-tools`). The folder name equals `name`. Command skills under `skills/pmo-docs/skills/` are Claude Code only and may use `disable-model-invocation`.
- Behaviour rules live only in `SKILL.md`. Other files link to it.
- Dependencies: PyYAML only, vendored in `skills/pmo-docs/scripts/_vendor/` (pure Python, `safe_load` only), so users install nothing. No new dependency without asking.
- Tests live in `tests/` and run on the one fake project, `examples/acme`, copied into a temp folder: `python3 -m unittest discover tests`. No network, no real data, nothing written outside a temp folder. CI runs them on every push.
- Python 3.10+, Linux and macOS (Windows through WSL): stdlib plus the vendored PyYAML, every script stops with a clear message below 3.10, answers `--help`, and reads and writes files as UTF-8.
- When a term changes, update `GLOSSARY.md` in the same change.

## Commits and changelog
- `CHANGELOG.md` is generated by git-cliff from commit messages (`cliff.toml`). Never edit it by hand.
- Prefer conventional commit subjects (`feat: ...`, `fix: ...`, `docs: ...`, `chore: ...`), one line, no body. Non-conventional commits are kept (under "Changed"); `chore`, `ci`, `test`, `style`, `build`, `refactor` and `docs(plan|dev|memory)` are left out of the changelog. The subject is the changelog line, so keep it readable and free of private names (`dev/scrub.sh` checks messages too). Breaking changes use `feat!:` or `fix!:`; bumping `schema_version` or renaming a config key or a template section is breaking.
- Dates in docs are UTC: `dev/release`, git-cliff and the tag use UTC, so a local-time date can differ by a day.
- Releasing: `dev/release [--bump] [--allow-dirty] [--dry-run] [version]` checks, writes the version into `SKILL.md` and `skills/pmo-docs/.claude-plugin/plugin.json` and the release tag into `README.md` and `docs/INSTALL_FOR_AGENTS.md` (install links, the agent prompt), runs git-cliff, then asks twice (commit and tag, push; default No, no `-y`). The release commit holds `CHANGELOG.md` and those four files, nothing else. Try it first with `--dry-run`. It ignores `memory.md` in the dirty check. A `v*` tag push triggers `.github/workflows/release.yml`, which zips `skills/pmo-docs` and publishes the GitHub release from the changelog section (it fails if that section is missing).

## Maintainer tasks
- **Tests and scrub:** `python3 -m unittest discover tests`; `bash dev/scrub.sh` (bash, not `sh`).
- **Evals** (twenty-eight cases in `evals/`, real agent runs, an estimated $4 for all on Sonnet with a Sonnet judge): `dev/run-evals [--case <name>]... [--runs N] [--jobs N] [--out DIR]` (all cases, 4 at once, Sonnet as agent and judge; the Haiku default judge splits its votes). Everything stays in one folder, `~/pmo-eval-runs/<UTC time>/`: `summary.log`, the plugin copy, and per case `eval.log`, `report.html` (the judges' reasons), `aggregate-result.json` and `sandbox-<n>/` (trace, session transcript, the project as the agent left it; never run git inside it). It builds a throwaway plugin copy because the plugin root is `skills/pmo-docs` and `claude plugin eval` needs `evals/` inside the plugin; plain `claude plugin eval` from the repo root never fires the skill. Use Sonnet (Haiku fails 5 of 9). Results are single samples and can flip, so re-run a failing case before changing `SKILL.md`. Prompts pin today's date. Grader lessons: an `llm` grader sees a file's path, not its text; `max: 0` needs `min: 0`; keep grader text short and positive; name output files in the prompt. Bash fails in the eval sandbox (`apply-seccomp ... setgroups`), so the agent cannot run the scripts and graders must not depend on Bash; the agent also runs in `dontAsk` mode, which denies Glob and Grep in the skill folder, so a playbook must name skill files by their exact `${CLAUDE_SKILL_DIR}/...` path.
- **SkillSpector** (before each release): scan a clean copy of the tracked files (a tree with `__pycache__` gives false findings) with `SKILLSPECTOR_PROVIDER=claude_cli SKILLSPECTOR_MODEL=sonnet skillspector scan skills/pmo-docs --baseline dev/skillspector-baseline.yaml`. A real result is SAFE with full coverage and every LLM call succeeded (`llm_calls_succeeded`); a cut-off run is not a result. Haiku reports false positives on the vendored PyYAML. Each LLM call is a `claude` session on the maintainer's plan. Avoid apostrophes in `config.default.yaml` comments (they break the static parser). Every baseline entry needs a reason.
- **Updating vendored PyYAML:** `dev/update-pyyaml <unpacked sdist>` (header has steps; `dev/pyyaml-prune.patch` is the cut; `_vendor/VERSION` is edited by hand).
- **Install check:** `dev/test-install.md`, in a throwaway `CLAUDE_CONFIG_DIR`.
- **Walkthrough check** (before each release): `dev/test-walkthrough.md`, in a throwaway `CLAUDE_CONFIG_DIR`. It runs the walkthrough's commands and the agent prompts; keep it in step with `docs/walkthrough.md`.

```
.trail/learnings/  committed learnings (rules only); .trail/cache/ is the repo graph
memory.md          project state for the next session (local, never committed)
```

## Session start
Read `memory.md`. When the user says **wrap-up**, update it with new rules (and why), state and open threads (absolute dates). Leave out what code or git history already hold.

## Trail — repo context graph

This repo is indexed in `.trail/cache/`: small linked markdown nodes that explain each
system and carry exact file:line spans, kept in sync with the code through git.

For ANY task here — understanding how something works, finding where code lives,
or scoping a change — get context from the graph before grepping or opening
source files. Re-ask freely (it's cheap) and reuse literal identifiers you
already have (symbol, error string, file name) as the query. New to this repo?
Run `trail map` first — a token-budgeted orientation (dir clusters, hubs,
hotspots), no LLM, no key.

- Run `trail ask "<your question>" --source` → ranked nodes with the relevant
  code spans inlined (each hit's ≤8-line crux by default; `--full` for whole
  definitions when the crux isn't enough). Match the tool to the task shape:
  for understanding or editing, the top node IS the answer — cite its
  `covers:` file:line spans and edit straight from `--source`. For
  exhaustive tasks ("every occurrence / every caller of this pattern"), ranked
  results are top-N, not complete — run `trail grep "<literal>"` instead
  (exhaustive over indexed files, grouped by enclosing symbol), falling back
  to raw `grep -rn` only for unindexed files.
- `trail skeleton <file>` → every definition's signature + span, ~10× cheaper
  than reading the file; use it to skim an API surface.
- `trail callers <symbol>` gives precomputed, exact edges — who calls this.
  Add `--direction out` for what it calls, or `--depth N` to walk
  transitively for the full blast radius. For structural questions, skip
  ranking and use this directly.
- Or browse: `.trail/cache/INDEX.md` lists every node; follow the links.
- Monorepos and folders of multiple repos rank fairly across sub-projects —
  hits carry `[scope/]` labels naming which one they're from. Narrow with
  `trail ask "<task>" --in <scope>/` once you know where you're working.

If a returned span is truncated ("+N more lines"), open the file at that exact
range before finalizing. Only open source files when a node genuinely lacks a
needed detail, and then at the exact file:line the node points to — never
re-read whole files.

After big code changes, refresh the graph with `trail build` (deterministic,
no API key, $0).

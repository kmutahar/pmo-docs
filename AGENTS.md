# pmo-docs

A project-office and documentation workflow packaged as an Agent Skill (`skills/pmo-docs/`). Plan hub and settled decisions: `docs/PLAN.md`; each version's plan: `docs/plans/`. Read the hub before changing anything structural. Use the words in `GLOSSARY.md`.

## Rules
- **Never commit or push without the maintainer's approval.** Never add `Co-Authored-By`, "Generated with Claude Code" or any attribution line to commits or PRs.
- **Never stage files.** The maintainer reviews edits and stages them. Never run `git add`, `git restore --staged` or `git rm --cached`. When asked to commit, use `git commit -- <paths>` (tracked files only; for a new file the maintainer runs `git add` first). Commit in chunks that follow the plan's task order, one subject per chunk; propose the chunks first. Never commit `memory.md`, and `docs/PLAN.md` only when told. Check `git status` before and after: staged state changes outside your session.
- **No private data in this repo (it is public).** No real names, roster slugs, emails, phone numbers, machine paths or client/project names from the source project. Enable the commit gate once per clone: `git config core.hooksPath .githooks` (pre-commit runs `dev/scrub.sh`, commit-msg checks the subject). Never use `--no-verify`. The names it checks live in the untracked `.scrub-names`.
- Fresh history only. Copy source files into `tmp/source/` (gitignored, inside this repo) and stage only generalised files; never import the source project's git history.
- Generic by default: anything project-specific comes from the user's `pmo/config.yaml`, never from the code or templates.
- `skills/pmo-docs/` must work alone (other agents load only the skill folder). `SKILL.md` uses only open Agent Skills fields (`name`, `description` up to 1024 chars, `license`, `compatibility`, `metadata`, `allowed-tools`). The folder name equals `name`. Command skills under `skills/pmo-docs/skills/` are Claude Code only and may use `disable-model-invocation`.
- Behaviour rules live only in `SKILL.md`. Other files link to it.
- Dependencies: PyYAML only, vendored in `skills/pmo-docs/scripts/_vendor/` (pure Python, `safe_load` only), so users install nothing. No new dependency without asking.
- Tests live in `tests/` and run on the one fake project, `examples/acme`, copied into a temp folder: `python3 -m unittest discover tests`. No network, no real data, nothing written outside a temp folder. CI runs them on every push.
- Python 3.10+, Linux and macOS (Windows through WSL): stdlib plus the vendored PyYAML. Every script stops with a clear message below 3.10, answers `--help`, and reads and writes files as UTF-8.
- When a term changes, update `GLOSSARY.md` in the same change.

## Commits and changelog
- `CHANGELOG.md` is generated by git-cliff from commit messages (`cliff.toml`). Never edit it by hand.
- Prefer conventional commit subjects (`feat: ...`, `fix: ...`, `docs: ...`, `chore: ...`), one line, no body. Non-conventional commits are kept (under "Changed"); `chore`, `ci`, `test`, `style`, `build`, `refactor` and `docs(plan|dev|memory)` are left out of the changelog. The subject is the changelog line: keep it readable and free of private names (`dev/scrub.sh` checks messages too). Breaking changes use `feat!:` or `fix!:`; bumping `schema_version` or renaming a config key or a template section is breaking.
- Dates in docs are UTC: `dev/release`, git-cliff and the tag use UTC, so a local-time date can differ by a day.
- Releasing: only the maintainer runs `dev/release` (it asks twice at the terminal; steps in `dev/release --help`). The agent may run it with `--dry-run`. The release commit holds `CHANGELOG.md` and the four version files (`SKILL.md`, `skills/pmo-docs/.claude-plugin/plugin.json`, `README.md`, `docs/INSTALL_FOR_AGENTS.md`), nothing else. A `v*` tag push triggers `.github/workflows/release.yml`, which fails if the changelog section is missing.

## Maintainer tasks
- **Tests and scrub:** `python3 -m unittest discover tests`; `bash dev/scrub.sh` (bash, not `sh`).
- **Evals, SkillSpector, vendored PyYAML update, install check, walkthrough check:** read `dev/maintaining.md` first, before writing or changing an eval case, touching `dev/` or preparing a release.

## Layout
- `skills/pmo-docs/` is all that ships: the marketplace manifest (`.claude-plugin/`) installs only that folder, so `dev/`, `tests/`, `docs/`, `evals/` and `examples/` do not ship. Its plugin manifest is `skills/pmo-docs/.claude-plugin/`.
- `examples/acme/` is the one fake project, used by tests, evals and `docs/walkthrough.md`.
- `PRIVACY.md` and `TERMS.md` are linked from `plugin.json`: update them when the skill starts reading or writing something new.
- `.trail/learnings/` is committed (rules only); `.trail/cache/` is the generated repo graph.
- `CLAUDE.md` only imports `AGENTS.md` and `memory.md`.

## Memory (`memory.md`)
Local, never committed. Read it at session start. On **wrap-up**, rewrite it, do not append:
- Keep an entry only if a later session would act differently without it and no other file holds it (`AGENTS.md`, the plans, code, `--help`, git history, learnings). If another file holds it, keep at most a pointer.
- Four sections, in this order: How the maintainer works (standing rules, one or two lines each, with the why), Decisions no other file holds, State, Open threads.
- State is replaced whole at every wrap-up: what is released, what is uncommitted, what is next. Ten lines at most. Check it against `git status -sb`, `git tag` and `git log` before writing, not against the old text.
- Open threads: delete one when it closes. Each has the date it was opened; ask about any older than 30 days, then close or drop it.
- No session stories: no "what worked" accounts, test counts, commit hashes, process ids, log paths or lists of deleted files. A lesson that outlives its task becomes a one-line rule, or a learning when it is about the repo and not about the maintainer.
- A rule replaces the one it corrects; never keep both. One absolute date per entry, only where the entry may be revisited.
- Keep it under 8,000 characters. When over, cut State detail and anything a file or command can answer.

## Trail — repo context graph

This repo is indexed in `.trail/cache/`: small linked markdown nodes that explain each
system and carry exact file:line spans, kept in sync with the code through git.

For ANY task here — understanding how something works, finding where code lives,
or scoping a change — get context from the graph before grepping or opening
source files. Re-ask freely (it's cheap) and reuse literal identifiers you
already have (symbol, error string, file name) as the query. New to this repo?
Run `trail map` first — a token-budgeted orientation (dir clusters, hubs,
hotspots), no LLM, no key.

- Run `trail ask "<your question>" --source` → ranked nodes with the relevant
  code spans inlined (each hit's ≤8-line crux by default; `--full` for whole
  definitions when the crux isn't enough). Match the tool to the task shape:
  for understanding or editing, the top node IS the answer — cite its
  `covers:` file:line spans and edit straight from `--source`. For
  exhaustive tasks ("every occurrence / every caller of this pattern"), ranked
  results are top-N, not complete — run `trail grep "<literal>"` instead
  (exhaustive over indexed files, grouped by enclosing symbol), falling back
  to raw `grep -rn` only for unindexed files.
- `trail skeleton <file>` → every definition's signature + span, ~10× cheaper
  than reading the file; use it to skim an API surface.
- `trail callers <symbol>` gives precomputed, exact edges — who calls this.
  Add `--direction out` for what it calls, or `--depth N` to walk
  transitively for the full blast radius. For structural questions, skip
  ranking and use this directly.
- Or browse: `.trail/cache/INDEX.md` lists every node; follow the links.
- Monorepos and folders of multiple repos rank fairly across sub-projects —
  hits carry `[scope/]` labels naming which one they're from. Narrow with
  `trail ask "<task>" --in <scope>/` once you know where you're working.

If a returned span is truncated ("+N more lines"), open the file at that exact
range before finalizing. Only open source files when a node genuinely lacks a
needed detail, and then at the exact file:line the node points to — never
re-read whole files.

After big code changes, refresh the graph with `trail build` (deterministic,
no API key, $0).

# pmo-docs

A project-office and documentation workflow packaged as an Agent Skill (`skills/pmo-docs/`). Read `skills/pmo-docs/SKILL.md` before changing anything structural. Use the words in `GLOSSARY.md`.

## Rules
- **Never commit or push without the maintainer's approval.** Never add `Co-Authored-By`, "Generated with Claude Code" or any attribution line to commits or PRs.
- **Never stage files.** The maintainer reviews edits and stages them. Never run `git add`, `git restore --staged` or `git rm --cached`. When asked to commit, use `git commit -- <paths>` (tracked files only; for a new file the maintainer runs `git add` first). Commit in chunks that follow the maintainer's untracked plan's task order (`tmp/plans/`), one subject per chunk; propose the chunks first. Never commit `memory.md`. Check `git status` before and after: staged state changes outside your session.
- **No private data in this repo (it is public).** Never include real names, roster slugs, emails, phone numbers, machine paths or source-project details (full checklist in `dev/maintaining.md`). Enable the commit gate once per clone: `git config core.hooksPath .githooks` (pre-commit runs `dev/scrub.sh`, commit-msg checks the subject). Never use `--no-verify`. The names it checks live in the untracked `.scrub-names`.
- Fresh history only. Copy source files into `tmp/source/` (gitignored) and keep only generalised files; never import the source project's git history.
- Generic by default: anything project-specific comes from the user's `pmo/config.yaml`, never from the code or templates.
- `skills/pmo-docs/` must work alone (other agents load only that folder). `SKILL.md` uses only open Agent Skills fields (`name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools`; limits and name rules in `dev/maintaining.md`, Naming rules). Command skills under `skills/pmo-docs/skills/` are Claude Code only and may use `disable-model-invocation`.
- Behaviour rules live only in `skills/pmo-docs/SKILL.md`. Other files link to it.
- Dependencies: PyYAML only, vendored in `skills/pmo-docs/scripts/_vendor/` (pure Python, `safe_load` only), so users install nothing. No new dependency without asking.
- Tests live in `tests/` and run on a temp copy of `examples/acme`: `python3 -m unittest discover tests`. No network, no real data, nothing written outside a temp folder. CI runs them on every push.
- Python 3.10+, Linux and macOS (Windows through WSL): stdlib plus vendored PyYAML. Every script stops with a clear message below 3.10, answers `--help`, and reads/writes UTF-8.
- When a term changes, update `GLOSSARY.md` in the same change.

## Commits and changelog
- `CHANGELOG.md` is generated by git-cliff (`cliff.toml`). Never edit it by hand.
- Prefer conventional one-line subjects (`feat:`, `fix:`, `docs:`, `chore:`), no body. Non-conventional commits are kept under "Changed"; `chore`, `ci`, `test`, `style`, `build`, `refactor` and `docs(plan|dev|memory)` stay out of the changelog. Keep subjects readable and scrubbed (`dev/scrub.sh` checks messages too). Breaking changes use `feat!:` or `fix!:`; bumping `schema_version` or renaming a config key or template section is breaking.
- Dates in docs are UTC (`dev/release`, git-cliff and tags use UTC).
- Releasing: only the maintainer runs `dev/release`; agents may run `--dry-run`. Full checklist, branch flow and version files live in `dev/maintaining.md`.

## Maintainer tasks
- **Tests and scrub:** `python3 -m unittest discover tests`; `bash dev/scrub.sh` (bash, not `sh`).
- **Evals, SkillSpector, PyYAML updates, install/walkthrough checks, releases:** read `dev/maintaining.md` first.

## Layout
- `skills/pmo-docs/` — the only folder that ships (`.claude-plugin/` installs only this folder; its plugin manifest is `skills/pmo-docs/.claude-plugin/`).
- `examples/acme/` — the fake project used by tests, evals and `docs/walkthrough.md`.
- `PRIVACY.md` and `TERMS.md` — linked from `plugin.json`; update when the skill reads or writes something new.
- `dev/`, `tests/`, `docs/`, `evals/` — maintainer tools, tests, guides and evals (not shipped).
- `.trail/`, `tmp/` and `claude-tests/` — local and untracked (`.gitignore`). `claude-tests/` holds an agent's scratch checks during development; the test suite is `tests/`.
- `CLAUDE.md` — imports `AGENTS.md`, `memory.md` and `lessons.md` only.

## Settled design choices
Do not reopen without a new reason:
- **Sparse project config:** `pmo/config.yaml` holds `schema_version` and only what differs from defaults (`null` removes a default map entry); a full copy pins keys so later defaults never reach the project.
- **No installed git hook or tool `git add`:** skill paths change across updates and machines, and `.git/hooks` is not shared; `pmo/bin/pmo` resolves the skill path instead.
- **Whole-file overrides:** an override replaces the whole default template or playbook; partial patches break silently when defaults change.
- **House rules boundary:** `pmo/house-rules.md` wins over the skill's rules except the safety rules and the definition of done.
- **Hash-based staleness:** Finish records a hash of each source register; exact and works without commits.

## Memory (`memory.md`) and lessons (`lessons.md`)
Both local, never committed. Read them at session start. On **wrap-up**, rewrite it, do not append:
- Keep an entry only if a later session would act differently without it and no other file holds it (`AGENTS.md`, the plans, code, `--help`, git history, learnings). If another file holds it, keep at most a pointer.
- Three sections, in this order: Decisions no other file holds, State, Open threads. Standing rules (one or two lines each, with the why) live in `lessons.md`, rewritten the same way on wrap-up.
- State is replaced whole at every wrap-up: what is released, what is uncommitted, what is next. Ten lines at most. Check it against `git status -sb`, `git tag` and `git log` before writing, not against the old text.
- Open threads: delete one when it closes. Each has the date it was opened; ask about any older than 30 days, then close or drop it.
- No session stories: no "what worked" accounts, test counts, commit hashes, process ids, log paths or lists of deleted files. A lesson that outlives its task becomes a one-line rule, or a learning when it is about the repo and not about the maintainer.
- A rule replaces the one it corrects; never keep both. One absolute date per entry, only where the entry may be revisited.
- Keep it under 8,000 characters. When over, cut State detail and anything a file or command can answer.

## Trail — repo context graph

This repo is indexed in `.trail/cache/`: small linked markdown nodes that explain each
system and carry exact file:line spans, kept in sync with the code through git.

For ANY task here — understanding how something works, finding where code lives,
or scoping a change — get context from the graph before grepping or opening
source files. Re-ask freely (it's cheap) and reuse literal identifiers you
already have (symbol, error string, file name) as the query. New to this repo?
Run `trail map` first — a token-budgeted orientation (dir clusters, hubs,
hotspots), no LLM, no key.

- Run `trail ask "<your question>" --source` → ranked nodes with the relevant
  code spans inlined (each hit's ≤8-line crux by default; `--full` for whole
  definitions when the crux isn't enough). Match the tool to the task shape:
  for understanding or editing, the top node IS the answer — cite its
  `covers:` file:line spans and edit straight from `--source`. For
  exhaustive tasks ("every occurrence / every caller of this pattern"), ranked
  results are top-N, not complete — run `trail grep "<literal>"` instead
  (exhaustive over indexed files, grouped by enclosing symbol), falling back
  to raw `grep -rn` only for unindexed files.
- `trail skeleton <file>` → every definition's signature + span, ~10× cheaper
  than reading the file; use it to skim an API surface.
- `trail callers <symbol>` gives precomputed, exact edges — who calls this.
  Add `--direction out` for what it calls, or `--depth N` to walk
  transitively for the full blast radius. For structural questions, skip
  ranking and use this directly.
- Or browse: `.trail/cache/INDEX.md` lists every node; follow the links.
- Monorepos and folders of multiple repos rank fairly across sub-projects —
  hits carry `[scope/]` labels naming which one they're from. Narrow with
  `trail ask "<task>" --in <scope>/` once you know where you're working.

If a returned span is truncated ("+N more lines"), open the file at that exact
range before finalizing. Only open source files when a node genuinely lacks a
needed detail, and then at the exact file:line the node points to — never
re-read whole files.

After big code changes, refresh the graph with `trail build` (deterministic,
no API key, $0).

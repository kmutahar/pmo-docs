# v0.4: stacks, technical and domain templates, and their registers

Status: planned, not started. Decided with the maintainer on 2026-11-06 (UTC). Hub, settled decisions and the version index: [`docs/PLAN.md`](../PLAN.md). Repo rules: [`AGENTS.md`](../../AGENTS.md). Words: [`GLOSSARY.md`](../../GLOSSARY.md). This plan builds on the code already released.

Each work package (W0 to W16) is self-contained: read it, the files it names and `AGENTS.md`, then start. Read other packages only if listed under "Needs".

## 1. Scope

**In v0.4**

| Theme | What ships |
|---|---|
| Technical drafting | `references/draft-technical.md`: the generic playbook for documents written from the code (inventory, read the code, fan out, record findings) |
| Stacks | `references/stacks/<stack>.md`, one page each, same headings: `nextjs`, `express`, `aspnet-core`, `spring-boot`, `fastapi` (also covers Flask), `django`, `flutter`. An unknown stack gets `pmo/playbooks/stacks/<stack>.md`, written once with the user |
| Templates | eight new doc types: `functional-requirements`, `test-acceptance`, `defect-gap-report`, `entity-lifecycle`, `api-reference`, `integration-guide`, `architecture-overview`, `user-guide`, each with a config entry and catalogue text |
| Registers | `requirements` (`REQ-`), `tests` (`TST-`), `environments` (`ENV-`), `permissions` (`PERM-`), with views, starter files copied on the first entry (not at setup) and Acme fixtures |
| Config | `domain.lifecycle_entity`, `domain.roles`, `technical.stacks`, `technical.consumers`, `registers.tasks.done`, per-register `refs` |
| Definition of done | with a `tests` register in use, the note `no test evidence recorded` is written when a task has no linked `tests` entry |
| Evals | one new case, `technical-draft-reads-code` |

**Not in v0.4**

- Playbook overrides: already in the skill.
- Schedule, scheduled refresh and the shared hook: a later version (hub). Repo sync: not planned (the skill never pulls).
- Graph-tool integration: no integration document; one sentence in `draft-technical.md` (D2).
- A sub-project concept and release notes per sub-project. The integration guide takes its consumers from a plain config list; the release-notes recipe takes `--repo PATH`.
- Generators for the new types. The agent drafts them from registers (the first four) or from the code (the other four).
- A script that checks a project's own stack file. The playbook lists the six headings; add a check to `docs_audit` if agents get them wrong.

## 2. Decisions (settled 2026-11-06)

| # | Topic | Decision |
|---|---|---|
| D1 | Theme | Stacks, technical and domain templates and their registers. Schedule, scheduled refresh and the shared hook come in a later version; repo sync is not planned. |
| D2 | `draft-technical.md` | Stays generic: pick the stack, inventory, read the code, fan out, record findings. One sentence: if the project has a code-graph or index tool, use it for the inventory step. No tool named, no separate integration document. |
| D3 | Stack files | `skills/pmo-docs/references/stacks/<stack>.md`, about one page (20 to 80 lines), all with the same six `##` headings in this order: `Routes, pages or screens`, `Data models`, `Permissions and auth`, `Config and environments`, `Tests`, `List the API live`. Front matter `playbook_version: 1`, then two plain lines before the `#` title (as a playbook's `Reads:` line): `Detected by: ...` and `Checked against: <framework and version>, <doc pages read>, <date>`. Each stack package reads the framework's official documentation and names the pages it read in that line, by title (the files hold no URL). Seven ship, chosen by Stack Overflow 2025 usage and project shape: `nextjs`, `express`, `aspnet-core`, `spring-boot`, `fastapi` (the file says it also covers Flask), `django`, `flutter`. |
| D4 | Unknown stack | The agent asks the user once, then, after a yes, writes `pmo/playbooks/stacks/<stack>.md` in the project with the same headings. The playbook lookup (project file wins, subfolders included) covers `stacks/`. The config key `technical.stacks` (list of stack names) names the stacks of the project; the agent may offer to set it, never sets it unasked. |
| D5 | Doc types | Eight: `functional-requirements`, `test-acceptance`, `defect-gap-report`, `entity-lifecycle`, `api-reference`, `integration-guide`, `architecture-overview`, `user-guide`. Written from scratch. `generated_from`: functional-requirements `[requirements]`; test-acceptance `[tests, requirements, environments]`; defect-gap-report `[tests, issues, requirements]`; entity-lifecycle `[permissions]`; api-reference `[environments, permissions]`; integration-guide `[environments, permissions]`; architecture-overview `[environments, decisions]`; user-guide `[requirements, permissions]`. `test-acceptance` and `defect-gap-report` read `requirements` for their coverage and gap sections; `test-acceptance` reads `environments` for its test environment section. |
| D6 | Template contract | Every template has the front matter of `status-report.md` (`title`, `type`, `project`, `manager`, `template_version: 1`, `status: draft`, `last_updated`, `period` only where named), `checks:`, a `<!-- Reads: ... -->` comment equal to `generated_from`, one `#` heading, a last section `## Open questions`, English only, no URL, no `{{owner}}` (use `{{lead}}`). The five that are read from the code (`entity-lifecycle`, `api-reference`, `integration-guide`, `architecture-overview`, `user-guide`) also carry `code_ref: "{{commit}}"` in the front matter: the commit the code was read at, so the docs-audit recipe can say how far behind a document is. A translation copies `code_ref` with the rest of the original's front matter (`references/conventions.md`, translation files). Each doc type gets `when` and `regenerate` text in config (the catalogue). `translate` is left unset: the default applies. |
| D7 | Domain config | `domain.lifecycle_entity` (text or null) names the entity of `entity-lifecycle`. `domain.roles` (list) names the permission roles; the `permissions` register checks its `roles` against it. A register `enums` entry may name a dotted config path (`domain.roles`) instead of a `vocab` list (W1). |
| D8 | Registers | `requirements`, `tests`, `environments`, `permissions`. One-line flow-mapping entries, prefixes `REQ`, `TST`, `ENV`, `PERM`. Every register has a `view` (the `render_views` pattern: a generic table of its fields) and a starter file. Setup creates none of the four; `track` creates each on its first entry. `tasks` gains the field `tests`. Links between registers are checked by a new optional per-register key `refs` (field to register; W1): an id that is not in the target register is a validation error; a target register that does not exist is skipped. |
| D9 | Integration guide consumers | A plain list `technical.consumers` (names). One row and one `###` section per name. No sub-project concept. |
| D10 | Definition of done | The note `no test evidence recorded` (today `SKILL.md`, Definition of done; also `govern.md` and `track.md`) is written when a task is marked done with no linked `tests` entry. A link is `tests: [TST-1]` on the task or `task: T-1` on the test. A project is "using tests" when its `tests` register has at least one entry; a project without entries keeps today's behaviour. The user's confirmation of QA stays required. |
| D11 | Done status in config | New optional key `registers.tasks.done: [done]` (like `registers.tasks.blocked` and `active`). The tasks view gains a line `**Done without a linked test:** T-5, T-9` (or `none`) when the project is using tests, and is unchanged otherwise. |
| D12 | No project commands unasked | Reading the code is read-only. A stack file's "List the API live" command is run by the user, or by the agent only after a yes. The agent never starts the app, builds, calls a URL or installs anything unasked. |
| D13 | No secrets | Registers and documents hold variable names, never values. The environments register has `variables` (names). If the code holds a secret value, the agent says where, without printing it. |
| D14 | Evals | One new case, `technical-draft-reads-code`: the draft names the routes found in a small fixture app and not guessable ones. Graders must not depend on Bash (`AGENTS.md`, grader lessons). |
| D15 | Schema version | Stays `1`. The new registers and keys are optional; a project without the new register files keeps validating. |
| D16 | Release | Explicit version `0.4.0` (W16), (hub section 8). |

**Code changes in `render_views.py`**

1. New function, used by `validate`:
   ```python
   def allowed(cfg, name):
       """Allowed values for an `enums` entry: a vocab name, or a dotted config path such as domain.roles. [] means any value."""
       if "." not in name:
           return cfg["vocab"].get(name) or []
       node = cfg
       for part in name.split("."):
           node = node.get(part) if isinstance(node, dict) else None
       return node if isinstance(node, list) else []
   ```
2. `validate`: in the `enums` loop use `ok = allowed(cfg, vname)` in place of `vocab[vname]`; keep every message text (`{who}: {field} {v!r} not in {ok}`) so existing tests stay green. Before the loop over registers build `ids = {n: {e.get("id") for e in rows} for n, rows in data.items()}`. After the dates loop add the `refs` check:
   ```python
   for field, target in reg.get("refs", {}).items():
       if target not in data:
           continue                      # the target register file does not exist: nothing to compare
       value = r.get(field)
       for v in value if isinstance(value, list) else [value]:
           if v not in (None, "") and v not in ids[target]:
               errors.append(f"{who}: {field} {v!r} is not an id in {target}")
   ```

### W3 Test evidence in the tasks view (Sonnet high)

**Goal:** the definition-of-done rule can be seen in the data: the tasks view lists done tasks that have no linked test.

**Code** (in `render_views.py`, pure functions, no printing):


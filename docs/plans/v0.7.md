# 0.7: teams

Status: planned. Hub and settled decisions: [`docs/PLAN.md`](../PLAN.md). Agent rules and the release checklist: hub section 8, except where section 3 below says otherwise.

Every earlier version is built for one writer per project. This version makes two or more writers safe: registers that conflict after a merge get clear messages, a duplicate id is fixed with one command, views list entries in id order, a draft names its editor, and the merge rules and a GitHub CI check are written down.

---

## 1. Scope

**In**

- **Clear register errors after a merge.** Leftover git conflict markers and duplicate ids are reported with `FILE:N` and the entry's label; two registers may not share a prefix.
- **Views sorted by id.** Every view of a register with ids lists entries by id number. Register files are never reordered.
- **Fixing duplicate ids.** `scripts/renumber.py` finds every duplicate id, gives the later copies the next free numbers, moves them to the end of their list, and rewrites only the references the user confirmed.
- **An editor per draft.** A draft may carry `editor: <roster slug>`. The current writer is named in the untracked `pmo/.me`. Before editing a draft whose `editor` is someone else, the agent says so and asks. No locks.
- **Merge rules and a GitHub CI check, written down.** In `references/git.md` (short) and `README.md` (with the full workflow).
- **Four eval cases** for the agent's judgement in these flows.

**Out**

- Locks, a server, or any network check in the skill.
- Writing `.github/workflows/` from a script, and any CI that commits.
- Duplicate roster slugs (the roster has no id).
- Git's `merge=union` for registers.

## 2. Decisions

| # | Topic | Decision |
|---|---|---|
| D1 | New ids | A new id is the highest number for the prefix plus one; a gap left by an old entry is never reused. Ids are never reused, renumbered or deleted, with one exception: a duplicate id after a merge, fixed only with `renumber.py`. |
| D2 | Which copy keeps the id | The first copy in the register file keeps the old id; `--line FILE:N` names a different keeper. Every other copy gets the next free number, in file order, and its line moves to the end of the list (where its new, highest id belongs). |
| D3 | References | A reference is a whole-word match of the old id, `(?<![A-Za-z0-9])T-5(?![A-Za-z0-9])`, anywhere on a register line other than the copies themselves (any field, not only the config's `refs`), and anywhere in a draft document (front matter or body). Finished documents are listed as left alone and never changed. Views are re-rendered, never searched. |
| D4 | Confirming references | With references, `--apply` needs one decision per reference line: `--rewrite FILE:N=NEW-ID` (change the old id on that line to `NEW-ID`) or `--keep FILE:N` (leave it). The dry run prints both ready-made flags for each reference so the agent picks one per line after one plain-English question to the user for the whole batch. Without references, `--apply` fixes everything in one step. |
| D5 | Paths | Every `FILE:N` printed or accepted by the scripts is the project-relative POSIX path plus a 1-based line number, for example `pmo/registers/tasks.yaml:7`. All `FILE:N` given to one run refer to the files as they were before that run. |
| D6 | Conflict markers | A register with conflict markers is resolved by hand under the merge rules (keep both sides' new lines; for an entry changed on both sides keep one version; delete the markers; run `renumber.py`). The scripts name the first marker line instead of printing a YAML error. |
| D7 | Prefixes | Two registers with the same prefix are a config error. |
| D8 | Sorting | Views sort by id number. Register files are never reordered by a script: their bytes are hashed for `source_hashes`, so reordering would make finished documents look stale. |
| D9 | Editor | `editor:` is optional draft front matter, written by the agent from `pmo/.me` when it creates a draft; it is not added to any template (a template key is required in every document). Finish keeps it. A mismatch gives a warning and a question, never a block. The agent asks "which roster person are you?" once and writes `pmo/.me` only when the roster has two or more people. |
| D10 | Schema version | Stays 1: no config key, register field or template section changes. |
| D11 | GitHub CI | Documented, never written by a script. `README.md` holds the full workflow, pinned to the released version in the link form `dev/release` already rewrites; `references/git.md` describes it in a few lines so the skill still works alone. `contents: read`; CI never commits. |

## 4. Work packages

### W1 Register errors and sorted views

**Goal:** after a merge, `render_views.py` says exactly what is wrong and where (D5, D6, D7), and views list entries by id (D8).

**Touches:** `skills/pmo-docs/scripts/render_views.py`, `skills/pmo-docs/scripts/generate.py` (one call), `tests/test_render_views.py`, `tests/test_render_views_edges.py`, `examples/acme/pmo/views/` (only if re-rendering changes them), `skills/pmo-docs/references/conventions.md`.

**Steps**

1. **Entry lines.** Add `entry_lines(text) -> list[int]`: the 1-based line numbers of the entry lines (`- ` lines after the top `name:` line, skipping blank and comment lines, the same rule as `one_line_entries`), in order, so `entries[i]` sits on line `entry_lines(text)[i]`. `renumber.py` reuses it.
2. **Conflict markers.** In `read_registers`, before the YAML parse, find the first line matching `^(<{7}|={7}|>{7})( |$)`. If there is one, report `pmo/registers/tasks.yaml:9: merge conflict markers; resolve them first (references/git.md, Several writers)` and skip that register.
3. **Duplicate ids.** `validate(data, cfg, root=None)`. Report one error per duplicated id (not one per extra copy), listing every copy:
   `duplicate id T-5: pmo/registers/tasks.yaml:7 "Write release notes", pmo/registers/tasks.yaml:8 "Fix login timeout"; run renumber.py`.
   - The label is the first of `title`, `text`, `name`, `item` that the entry has. Without one, print no label.
   - With `root=None`, positions are `tasks entry 7` (the 1-based entry index).
   - `main()` and `generate.py` (line 879) pass `root`. Callers that pass no `root` keep working, and the existing tests that look for `duplicate id T-1` still pass.
4. **Prefixes.** In `config_errors`, two registers with the same `prefix` give `registers tasks and tests both use prefix T`.
5. **Sorted views.** In `render()`, for a register whose `fields` include `id`, sort rows by `(_id_num(id), file position)` before building the table. Registers without ids (roster, capacity) keep file order. In `view_tasks`, each team/group list sorts by priority, then id number.
6. Re-render `examples/acme/pmo/views/`. Commit the views only if they changed.

**Tests:**
- Conflict markers give the message with `FILE:N`, and exit 1.
- A duplicate with two copies gives one error with both positions, both titles and the `renumber.py` hint. Three copies give one error with three positions.
- A duplicate in a register whose entries have `text` instead of `title` shows the `text` label.
- `validate` without `root` still reports `duplicate id`.
- A shared prefix is a config error, exit 2.
- A register written out of order (T-3, T-1, T-2) renders in id order, and the register file is unchanged byte for byte.
- The tasks view orders ties by id.
- `generate.py` still refuses duplicates (the existing test).

**Docs:** `references/conventions.md`: views list entries by id number, and the two new `render_views.py` messages.

**Done when:** the tests above pass with the whole suite, the scrub is clean, and `render_views.py --check` on a fresh Acme copy prints `registers valid, views current`.

### W2 renumber.py

**Goal:** a duplicate id is fixed in one step when nothing references it, or after one batch confirmation when something does (D1 to D5).

**Touches:** `skills/pmo-docs/scripts/renumber.py` (new), `tests/test_renumber.py` (new), `evals/renumber-batch-confirm/` (new), `skills/pmo-docs/SKILL.md`, `skills/pmo-docs/references/track.md`, `skills/pmo-docs/references/conventions.md`, `GLOSSARY.md`, `AGENTS.md`.

**CLI:** `renumber.py [<ID>] [--line FILE:N] [--apply] [--rewrite FILE:N=NEW-ID]... [--keep FILE:N]... [--project ROOT]`

The script uses the same skeleton as `overdue.py`:
- a module docstring with usage and exit codes,
- `--help`,
- the Python version check,
- UTF-8 reads and writes through `pmo_common`,
- `pc.add_project_arg`.

**Finding duplicates**

1. Load the config and stop with exit 2 on `config_errors`. Read the registers with `render_views.read_registers`. If it reports any error, print it and exit 1, without writing anything.
2. For every register with an `id` field, in config order, find ids that appear on more than one entry line (`entry_lines`). With `<ID>`, keep only that id. With `--line FILE:N`, that line's id is the one handled, and the line is its keeper.
3. Keeper: the first copy in the file, or the `--line` copy. Every other copy, in file order, gets the next free number: the highest number for the prefix in that register plus one, then plus two, and so on.
4. References: every match of the old id under D3. Leave out the copies' own lines. Register lines come in config order, then drafts, then finished documents. Search all `*.md` under `paths.documents`, recursively. A document is a draft when its front matter has `status: draft`. Every other document is finished and is listed as left alone.

**Dry run** (no `--apply`) prints, per duplicate id:

```
duplicate T-5 in pmo/registers/tasks.yaml
  keeps T-5  pmo/registers/tasks.yaml:7  "Write release notes"  owner alice
  gets  T-6  pmo/registers/tasks.yaml:8  "Fix login timeout"  owner bob
  references:
    pmo/registers/changes.yaml:3  CR-3 "Add dark mode"  in related_tasks
      --rewrite pmo/registers/changes.yaml:3=T-6  |  --keep pmo/registers/changes.yaml:3
    'pmo/documents/2026-03 - Status report.md:41'  draft  T-5 is blocked by the vendor
      --rewrite 'pmo/documents/2026-03 - Status report.md:41=T-6'  |  --keep 'pmo/documents/2026-03 - Status report.md:41'
  left alone (finished): pmo/documents/Decision log.md:12
```

- A register reference shows the entry id, its label (the same rule as W1) and the field names that hold the old id.
- A document reference shows `draft` and the line text trimmed to 100 characters.
- Flags are shell-quoted (`shlex.quote`).
- Owner is printed when the entry has one.
- The run ends with one next-step line: `next: renumber.py --apply` when no reference needs a decision, otherwise `next: choose --rewrite or --keep for each reference, then renumber.py --apply <flags>`.

**`--apply`**

1. Check everything before writing anything:
   - Each `--rewrite`/`--keep` line must be a listed reference.
   - Each `NEW-ID` must be one of the new ids for a duplicate whose old id is on that line.
   - No line may get two decisions.
   - Every listed reference must have a decision.

   Any failure: print the problem and exit 2, with nothing written.
2. On each moving copy, change only the `id:` value (`id: T-5` becomes `id: T-6`, matching `id:\s*T-5(?=[,}\s])`) and move the line to just after the last entry line of its register.
3. On each `--rewrite` line, replace every whole-word match of the old id whose prefix matches `NEW-ID` with `NEW-ID`. `--keep` lines are not touched.
4. Write the changed files, then re-render the views by calling `render_views.main(["--project", root])` the way `setup.py` does (capture its output, print it).
5. Print every changed line as `changed: FILE:N  <new line>`, with its position after the run.

**Exit codes:**
- **0:** no duplicates, or `--apply` fixed every duplicate and the views were written.
- **1:**
  - the dry run found duplicates;
  - registers are unreadable (YAML error, conflict markers);
  - after `--apply`, duplicates remain (for example when `<ID>` narrowed the run);
  - after `--apply`, validation fails for another reason. Here the registers were changed and the views were not written, and the message says so.
- **2:** usage errors:
  - config errors;
  - an `<ID>` that is not duplicated;
  - a `--line` that holds no duplicate;
  - a bad, unknown or missing `--rewrite`/`--keep`.

**Writes:** only files under `paths.registers`, draft documents under `paths.documents`, and `paths.views`. No git commands.

**Tests** (`tests/test_renumber.py`, temp Acme copy, `subprocess` with `sys.executable`):
1. No arguments on clean Acme: exit 0, `no duplicate ids`, nothing changed.
2. Add a second `T-5`. The dry run exits 1 and shows the keeper, the new id `T-6`, titles and owners.
3. `--apply` with no references: one step. The id changes, the line is last in the list, `render_views.py --check` passes, and nothing else in the file changes.
4. With references in `changes.yaml` (`related_tasks`), `dependencies.yaml` (`from:`) and a draft document:
   - the dry run lists each one with its snippet and both flags;
   - `--apply` without decisions exits 2 and writes nothing;
   - `--apply` with one `--rewrite` and one `--keep` changes only the rewritten line.
5. A finished document that mentions the id is unchanged byte for byte and listed as left alone.
6. Three copies of `T-5`: they become T-5, T-6, T-7, and `--rewrite FILE:N=T-7` works.
7. `--line` makes the second copy the keeper.
8. Prefixes do not bleed: duplicate `DEC-2` while `D-2` exists. `D-2` lines are never references and never change. The same holds for `T` and `TST`/`TM`, and `A` and `ACT`.
9. Duplicates in two registers at once (`T-5` and `M-3`) are fixed in one `--apply`.
10. `<ID>` narrowing leaves the other duplicate: exit 1.
11. `<ID>` that is not duplicated: exit 2. A `--rewrite` on a line that is no reference: exit 2.
12. A register with conflict markers: exit 1 with the W1 message, nothing written.

**Eval** `evals/renumber-batch-confirm/` (same files as `evals/ids-and-bulk-edits/`):
- **Scaffold:** copies Acme, adds a second `T-5` ("Fix login timeout", owner bob), a change `CR-3` with `related_tasks: [T-5]` whose title is clearly about the login fix, and a dependency whose text is clearly about the release notes.
- **Prompt:** pins today's date, says not to use an interactive form, gives the `renumber.py` dry-run output verbatim (in the format above), and asks the agent to prepare the fix. It must name the flags it would pass in its final answer.
- **Graders:**
  - an `llm` grader passes when the answer asks one plain-English confirmation for the batch, matches `CR-3` to T-6 (`--rewrite`) and the dependency to T-5 (`--keep`), and does not claim to have changed anything;
  - `tool_used` `Edit` and `Write` on `registers/` with `min: 0`, `max: 0`.

**Docs**
- `SKILL.md`:
  - the Ids rule (line 71) gets the D1 exception, word for word: "Never reuse, renumber or delete an id, except a duplicate id after a merge, which `renumber.py` fixes.";
  - `allowed-tools` gets `Bash(python3 ${CLAUDE_SKILL_DIR}/scripts/renumber.py *)`;
  - the Scripts table gets `scripts/renumber.py [<ID>] [--apply]` (fix duplicate ids after a merge).
- `references/track.md`: when validation reports a duplicate id, run `renumber.py`. With no references, run `--apply`. With references, match each reference to a copy by its title, owner and context, ask the user once for the whole batch in plain English, then run `--apply` with the flags.
- `references/conventions.md`: flags and exit codes.
- `GLOSSARY.md`: Renumber.
- `AGENTS.md`: eval count to twenty-nine.

### W4 Merge rules and CI check

**Goal:** a team knows how to merge each kind of file, and can make GitHub fail a pull request with a duplicate id or a stale view (D6, D11).

**Touches:** `skills/pmo-docs/references/git.md`, `README.md`, `evals/merge-conflict-markers/` (new), `AGENTS.md`.

**`references/git.md`:** a section `## Several writers`.
- **Registers:** for a conflict, keep both sides' new lines, keep one version of an entry changed on both sides, delete the marker lines, then run `render_views.py`. For a duplicate id, run `renumber.py` (`references/track.md`).
- **Views:** never merged by hand; render again.
- **Drafts:** resolve by hand, then `structure_check.py`.
- **Finished documents:** never merged; a second finished version is a new draft.
- **CI check, a few lines:**
  - a GitHub Actions workflow can run the same check as the hook;
  - it downloads the skill at the installed version (`metadata.version` in `SKILL.md`) from the release archive and sets `PMO_DOCS_SKILL` to its `skills/pmo-docs` folder;
  - it runs `pmo/bin/pmo render_views --check` on pushes and pull requests that touch `pmo/**`, with `permissions: contents: read`;
  - it never commits;
  - the README has the full file.

**`README.md`:**
- **"Two writers" section:** a short summary that links to `references/git.md` for the rules, next to "Check the registers in your own git hook".
- **The full workflow** (below), with the version written as the current release, `0.6.0`. `dev/release` rewrites `refs/tags/v<old>` and `pmo-docs-<old>/skills` to the new version at release, so the README always holds the released version. Copy the repo URL from the README's install links.
- **Roadmap row:** 0.7 teams.
- **"Limits":** no locks; an editor is a warning, not a lock.

```yaml
name: pmo check
on:
  push: { paths: ["pmo/**"] }
  pull_request: { paths: ["pmo/**"] }
permissions: { contents: read }
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: curl -fsSL https://github.com/<owner>/pmo-docs/archive/refs/tags/v0.6.0.tar.gz | tar -xz
      - run: pmo/bin/pmo render_views --check
        env: { PMO_DOCS_SKILL: pmo-docs-0.6.0/skills/pmo-docs }
```

**Eval `merge-conflict-markers`:**
- **Scaffold:** copies Acme and writes git conflict markers in `tasks.yaml` around two `T-5` lines with different titles. The prompt asks to fix the tasks register after a merge.
- **Graders:** an `llm` grader passes when the answer says it kept both tasks, removed the markers, and that a duplicate id remains for `renumber.py`; a `file_exists` or `tool_used` grader checks that `tasks.yaml` was edited.
- **`AGENTS.md`:** eval count to thirty-two, and the cost estimate to an estimated $5.

**Done when:**
- the whole suite passes and the scrub is clean;
- `tests/test_release.py` still passes;
- after the W4 commit (`dev/release` refuses while `README.md` is modified), `dev/release --dry-run 0.7.0` shows the README workflow lines changing to `0.7.0`.

# v0.5: other agents and unattended runs

Status: planned. Packages have no code signatures because they build on the released code. Decided with the maintainer on 2026-11-06 (UTC). Hub and settled decisions: [`docs/PLAN.md`](../PLAN.md). Agent rules and the release checklist: hub section 8.

One theme: running the skill where `${CLAUDE_SKILL_DIR}` is not set and the plugin path is unknown. Other agents, cron, a shared git hook and scheduled refresh all need the same thing, so they ship together.

---

## 1. Scope

**In**

- A project launcher, `pmo/bin/pmo`, that finds the installed skill and runs one of its scripts.
- Other agents tried by hand: Codex, Gemini CLI, Cursor, Copilot.
- Schedule: an optional config list that records what runs when; the agent prints the line for the user to install.
- Scheduled refresh (views rendered on a schedule) and a shared git hook, both through the launcher, both documented, neither installed by the skill.
- README: one install section per agent that passes.
- An install document for agents, `docs/INSTALL_FOR_AGENTS.md`: the user gives any agent one prompt that points at it, and the agent installs and verifies the skill for itself (D10).

**Out**

- Repo sync: the skill never pulls (`SKILL.md` safety rule 1). A user who wants it adds their own `git pull` line next to the schedule; `schedule.md` says so in one sentence.
- Portable prompt and cheatsheet, unless W3 finds an agent that cannot load skill folders (D5).

## 2. Decisions (settled 2026-11-06)

| # | Topic | Decision |
|---|---|---|
| D1 | Launcher | `setup.py` writes `pmo/bin/pmo`, a short POSIX `sh` script, checked in with the project. `pmo/bin/pmo <script> [args]` runs `python3 <skill>/scripts/<script>.py [args]` from the project root, taken from the launcher's own location (`$0`, two folders up), whatever the caller's folder; the script gets `--project <root>`. No absolute path is written into it. |
| D2 | Lookup order | `$PMO_DOCS_SKILL` if set; else the first `pmo-docs` folder in the project under `.claude/skills`, `.agents/skills`, `.github/skills`, `.cursor/skills`, `.gemini/skills`; else the newest `pmo-docs` version in the Claude plugin cache under `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/plugins/cache/` (by `plugin.json` version); else the first one under `~/.claude/skills`, `~/.agents/skills`, `~/.copilot/skills`, `~/.cursor/skills`, `~/.gemini/skills`. The folders are the ones the agents' docs list (checked 2026-11-11 UTC); none of the four other agents documents an equivalent of `${CLAUDE_SKILL_DIR}`. A folder counts only when it holds `SKILL.md` and `scripts/`. A set `PMO_DOCS_SKILL` that is not valid exits 2 and does not fall through. Nothing found: exit 2, `pmo-docs not found: set PMO_DOCS_SKILL`. |
| D3 | Version check | None in the launcher. The scripts already refuse a project with a newer `schema_version` (exit 2); the launcher passes the exit code through. |
| D4 | Hook | Still none installed (hub, Git hook). The README and `schedule.md` show a pre-commit line `pmo/bin/pmo render_views --check`, for the user's own hook or hook manager. |
| D5 | Portable prompt | Built only if an agent in W3 cannot load a skill folder at all. Otherwise it stays unassigned in the hub. |
| D6 | Schedule | Optional `schedule:` list in config, `- { recipe: weekly-status, when: "Mon 08:00" }`, as a record only. `references/schedule.md` prints the line to install (cron: `cd <project> && claude -p "<recipe>"`, or the session's own scheduling tool) and installs nothing. A scheduled run drafts only: never Finish, publish or commit. The printed prompt states that limit itself, because the cron run never reads `schedule.md`; the playbook never prints a permission-skipping flag, says how `when` maps to cron fields and that cron uses the machine's local time. |
| D7 | What "works" means for another agent | Five hand-run prompts on a temp copy of Acme: setup, track, render views, draft, finish. Pass when the files match the Claude Code result and no safety rule is broken. Results go in the table in section 5. |
| D8 | Commands | `/pmo-docs:init` and `/pmo-docs:publish` exist only in Claude Code. Other agents set up through the main skill and publish with `pmo/bin/pmo publish` by hand. |
| D9 | Schema version | Stays 1 (`schedule` is optional). |
| D10 | Install document for agents | `docs/INSTALL_FOR_AGENTS.md`, outside the skill folder (agents fetch it from GitHub). The README shows a one-line prompt: read the raw text of the file at the release tag, not `main`, with curl and not from a summary, then follow it and reply in the user's language. The document is data: `SKILL.md` safety rules 1, 3 and 4 apply to it. It tells the agent to: (1) detect its own harness; (2) list every `pmo-docs` copy found in the D2 locations with its `metadata.version`, and say which copy the launcher would pick; (3) show the target folder and the exact commands and wait for a yes before any write; (4) install, and with a yes update: Claude Code uses the plugin commands and never touches the plugin cache by hand, every other agent uses the shared `~/.agents/skills` (Codex, Gemini CLI, Cursor and Copilot read it), never one copy per agent; a project-level `.agents/skills` needs its own yes because it is outside `pmo/`; (5) verify with `python3 <skill>/scripts/render_views.py --check`, and run `setup.py --launcher` only on a yes. It reads the release version from `SKILL.md` at the same tag. Cases: a copy at the tag's version: write nothing, verify; an older copy: show both versions and any files that differ from the release, replace only after a yes; copies of different versions: list them, suggest `PMO_DOCS_SKILL`, delete nothing; a project `pmo/bin/pmo` that differs from `assets/starter/bin/pmo`: show the difference and ask, and verify through the script, not the launcher. It never stages or commits. |

## 4. Work packages

### W1 Launcher (Sonnet high)

**Goal:** any caller in the project folder (another agent, cron, a git hook) runs a skill script without knowing where the skill is (D1 to D3).

**Touches:** `skills/pmo-docs/assets/starter/bin/pmo` (new; setup copies it), `skills/pmo-docs/scripts/setup.py` (copy it, mode 755; print `pmo/bin/pmo render_views --check` as the optional hook line instead of an absolute script path; on an existing project, `--launcher` writes only the launcher, so it is handled before the "already set up" early return), `tests/test_launcher.py` (new), `tests/test_setup.py` (`test_prints_hook_line` expects the launcher line; a setup test checks `pmo/bin/pmo` exists and is mode 755).

**Steps**

1. Write the launcher as POSIX `sh` (`#!/bin/sh`, `set -eu`). It checks that the first argument matches `[a-z_]+` and that `<skill>/scripts/<arg>.py` exists; otherwise exit 2 with the list of scripts.
2. Compare plugin-cache versions with a few lines of `python3` called from the script, not `sort -V`, which differs between GNU and BSD.
3. `exec python3 "<skill>/scripts/<script>.py" "$@"`, so the exit code passes through.
4. `setup.py`: copy the launcher to `pmo/bin/pmo` and set mode 755. New flag `--launcher`: on an existing project, write only that file. On a fresh setup an existing launcher is kept and printed as `kept:` (new one `created:`). If a launcher exists and differs, write nothing, say so, and exit 1 (there is no `--force` today; the user deletes the old file to replace it).

**Tests** (fake install trees in a temp `HOME` and `CLAUDE_CONFIG_DIR`; never the real ones):

- `PMO_DOCS_SKILL` wins over everything; a project skill folder wins over the cache, and the cache wins over a user-level folder.
- Two cached versions `0.4.0` and `0.10.0`: `0.10.0` is chosen.
- Nothing installed: exit 2 with the message.
- `pmo/bin/pmo render_views --check` on a temp Acme (the starter launcher copied into it; `examples/acme` itself stays unchanged) exits like the script itself (0, then 1 after editing a view).
- A bad script name (`../x`, `rm`) exits 2 and runs nothing.
- `PMO_DOCS_SKILL` pointing at an invalid folder exits 2; a folder without `SKILL.md` or `scripts/` is skipped; the launcher run from a subfolder uses the project root.
- `test_no_tool_stages_or_commits` also scans the launcher, and `test_plugin.test_no_forbidden_folders` (no `bin/` at the repo root; the launcher lives under `assets/starter/bin/`) still pass.
- `--launcher` on an existing project writes only the launcher; a different existing launcher is left alone and exits 1.

**Notes for W5:** README section "Running outside a session"; `conventions.md`: the launcher, its lookup order and exit codes; `setup.md`: the launcher is written at setup; `GLOSSARY.md`: Launcher; `references/git.md`: the hook example uses the launcher instead of `PMO_DOCS=/path/...`.

**Done when:** tests pass on Linux, and on macOS if available (else say so); full suite and scrub pass.

**Status:** done (2026-11-11, tests and scrub pass on Linux; macOS not tried).

### W2 Schedule (Sonnet high)

**Goal:** the user can record a schedule and get the exact line to install (D6).

**Touches:** `skills/pmo-docs/assets/config.default.yaml` (`schedule: []` with a comment), `skills/pmo-docs/scripts/render_views.py` (`config_errors`: each item has `recipe`, a known recipe name, and `when` as text; the known names are a constant in `render_views.py` plus any `<name>.md` under `paths.playbooks` (a project can add recipes, `extend.md`): `weekly-status`, `monthly-status`, `month-start`, `overdue-report`, `docs-audit`, the recipes `SKILL.md` routes by name), `skills/pmo-docs/references/schedule.md` (new, with `playbook_version: 1`), `tests/test_render_views.py`.

**Steps**

1. Config key and validation as above.
2. `schedule.md`: ask which recipe and when; write the `schedule` entry only after a yes (`SKILL.md`, ask before writing beyond the request); print the cron line or the session-scheduler call; say that scheduled runs only draft; show the optional refresh line `pmo/bin/pmo render_views` and the hook line (D4); one sentence on repo sync (Out).
3. Do not: install a cron entry, write a hook, Finish, publish or commit.

**Tests:** a valid `schedule` passes; a recipe that exists only as a project playbook passes; an unknown recipe and a missing `when` are config errors.

**Notes for W5:** `SKILL.md` routing row "to run a recipe on a schedule" → `references/schedule.md`; `conventions.md`: the `schedule` key.

**Done when:** tests pass; full suite and scrub pass.

**Status:** done (2026-11-11).

### W3 Agent trials (maintainer; Haiku low writes the checklist)

**Goal:** a measured result per agent (D7).

1. Haiku writes `dev/agent-trial.md`: install steps per agent (where it looks for skill folders: the D2 list, re-checked against each agent's own docs), the five prompts, and the files each prompt should leave in a temp copy of Acme (taken from a Claude Code run of the same prompts).
2. The maintainer gives each agent the D10 prompt, so the install itself is part of the trial, then runs the five prompts and fills the table in section 5: skill found, front matter read, scripts ran (directly, through the launcher, or not at all), each prompt pass or fail, safety rules kept.
3. Switch trial: agent A sets up and edits, then agent B takes the D10 prompt on the same project. Pass when B writes nothing but verifies, and B's render leaves the views unchanged.
4. A failure gets one line: what happened and which file is likely at fault.

**Done when:** every agent has a row.

**Status:** done (2026-11-11). Codex and Antigravity tested; Gemini CLI, Cursor and Copilot are untested.

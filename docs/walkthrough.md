# Walkthrough: the Acme project

`examples/acme` is a small made-up project, "Acme Portal", with a project manager and two team leads. The tests use the same files. This page runs the skill's scripts on a copy of it, so you can see what each one does before you use it on a real project. The date for Acme is 2026-03-15.

Every command and output below was run on a fresh copy. Work on a copy, not in the repo:

```sh
cp -r examples/acme /tmp/acme && cd /tmp/acme
SKILL=/path/to/skills/pmo-docs     # the skill folder in a clone of this repo: skills/pmo-docs
```

The skill's behaviour rules are in [`SKILL.md`](../skills/pmo-docs/SKILL.md); this page only shows the results. The words (register, view, document, ...) are defined in [`GLOSSARY.md`](../GLOSSARY.md).

## What Acme contains

```
pmo/
  config.yaml      project name and manager only
  registers/       20 registers, one entry per line
  views/           one view per register plus the catalogue, rendered from them
  documents/       a status report and a decision log, both drafts
```

The config holds only the settings Acme changes (`schema_version`, the project name and the project manager). Everything else comes from the skill's defaults. The people are in the roster register:

```yaml
roster:
  - {slug: sam, name: Sam Example, role: Project manager}
  - {slug: alice, name: Alice Example, role: Platform lead}
  - {slug: bob, name: Bob Example, role: Web lead}
```

A task is one line. Its `owner` is a roster slug:

```yaml
  - {id: T-1, title: Set up staging server, team: platform, group: infra, priority: high, owner: alice, status: in-progress, due: 2026-03-10, period: 2026-03, notes: Overdue on purpose}
```

## 1. Validate the registers and compare the views

```
$ python3 "$SKILL/scripts/render_views.py" --check
registers valid, views current
[exit 0]
```

`--check` writes nothing. It exits 1 when a register has an error or a view is out of date.

## 2. Change a register, then render

Mark the login page design (`T-2`) done by editing its line in `pmo/registers/tasks.yaml`: change `status: not-started` to `status: done`. The view still shows the old state, so the check fails:

```
$ python3 "$SKILL/scripts/render_views.py" --check
ERROR stale view: pmo/views/tasks.md
[exit 1]
```

Render the views again. Views are never edited by hand:

```
$ python3 "$SKILL/scripts/render_views.py"
registers valid; wrote 21 views to pmo/views
[exit 0]

$ python3 "$SKILL/scripts/render_views.py" --check
registers valid, views current
[exit 0]
```

A value that is not in the vocabulary is reported instead. With `status: bogus` on that line:

```
$ python3 "$SKILL/scripts/render_views.py" --check
ERROR tasks T-2: status 'bogus' not in ['not-started', 'in-progress', 'blocked', 'done', 'dropped']
[exit 1]
```

Put the line back before going on (`status: not-started`), then render again.

A view is plain Markdown. This is `pmo/views/risks.md`:

```
<!-- GENERATED by render_views.py from pmo/registers/risks.yaml. Do not edit; edit the register. -->

# Risks

| id | title | description | probability | impact | owner | mitigation | status | origin | raised | closed |
|---|---|---|---|---|---|---|---|---|---|---|
| R-1 | Vendor delay | Payment vendor may reply late | high | high | bob | Ask two vendors | open | stated | 2026-02-10 |  |
| R-2 | Key person away | Alice may be on leave in April | low | medium | sam | Share the setup notes | closed | stated | 2026-02-10 | 2026-03-01 |
```

## 4. Where a document lives

`where.py` answers "which file, which template, which registers" so nobody works the paths out by hand:

```
$ python3 "$SKILL/scripts/where.py" status-report 2026-03 --hashes
type: status-report
title: Status report
document: pmo/documents/2026-03 - Status report.md
document_exists: yes
template: <skill folder>/assets/templates/status-report.md
template_source: skill
template_exists: yes
template_version: 1
based_on: none
drift: n/a
generated_from: tasks, milestones, risks, issues, changes, actions, decisions, teams
stale_days: 30
window: 2026-03-01..2026-03-31
translations: none
translate: in-period
source_hashes: {tasks: "86d95355", milestones: "0e9469b7", risks: "a9268ee2", issues: "fcc3f6b0", changes: "5351a37c", actions: "3c2a3948", decisions: "988ad57c", teams: "e2679193"}
[exit 0]
```

The `template` line shows the full path on your machine; it is shortened here. `generated_from` lists the registers a status report is made from. `source_hashes` is what Finish records in a finished document, so that a later change to one of those registers can be noticed (the document is then stale). `translations` and `translate` say which languages the type is translated into and when; Acme writes English only (section 6).

## 5. Check the documents

```
$ python3 "$SKILL/scripts/structure_check.py"
ok    pmo/documents/2026-03 - Status report.md
ok    pmo/documents/Decision log.md

0 file(s) with structure errors
[exit 0]
```

The check compares each document with its template: the headings, the tables and the checks the template declares. Rename a heading in the status report (`## Summary` to `## Overview`) and it fails:

```
$ python3 "$SKILL/scripts/structure_check.py" "pmo/documents/2026-03 - Status report.md"
ERROR pmo/documents/2026-03 - Status report.md: heading `## Summary` is missing
warn  pmo/documents/2026-03 - Status report.md: extra sections: Overview

1 file(s) with structure errors
[exit 1]
```

Both Acme documents are drafts. `docs_audit.py` looks for stale, old and broken documents and exits 1 when it finds any:

```
$ python3 "$SKILL/scripts/docs_audit.py" --as-of 2026-03-15

```

## 6. Languages and translations

Acme has no `languages` block, so it writes English only. Add one to `pmo/config.yaml` to translate documents into a second language (`xx` is an invented code):

```yaml
languages:
  translations: [xx]
  xx: { label: XX, dir: rtl, glossary: pmo/data/glossary-xx.md }
```

`render_views.py --check` validates the new keys (it still prints `registers valid, views current`). `where.py --lang` then gives the translation's path, the value for its `translation_of` and the `source_hash` of the original's body:

```
$ python3 "$SKILL/scripts/where.py" decision-log --lang xx --hashes
type: decision-log
title: Decision log
document: pmo/documents/Decision log.xx.md
document_exists: no
original: pmo/documents/Decision log.md
original_exists: yes
translation_of: "Decision log.md"
lang: xx
dir: rtl
glossary: pmo/data/glossary-xx.md
glossary_proposed: pmo/data/glossary-xx.proposed.md
template: <skill folder>/assets/templates/decision-log.md
template_source: skill
template_exists: yes
template_version: 1
based_on: none
drift: n/a
generated_from: decisions
stale_days: 30
window: none
translations: xx
translate: in-period
source_hash: "f1bea050"
[exit 0]
```

A type that is not translated refuses the flag. The shipped defaults translate neither the audit report nor the overdue report:

```
$ python3 "$SKILL/scripts/where.py" docs-audit-report --lang xx
usage: where.py [-h] [--project PROJECT] [--week] [--as-of YYYY-MM-DD]
                [--hashes] [--title TITLE] [--lang CODE]
                type [period]
where.py: error: doc type 'docs-audit-report' has no translations configured
[exit 2]
```

`parity_check.py` compares each translation with its original: the same headings, tables, ids, numbers, list items and ticked boxes. Acme has no translation yet:

```
$ python3 "$SKILL/scripts/parity_check.py"

0 file(s) differ from their originals
[exit 0]
```

The agent writes the translation with the `translate` playbook, and only when asked. `docs_audit.py` then reports a translation whose original changed afterwards (`Translation behind`) and every parity difference (`Parity`). Generators write English only.

## 7. With the agent

In Claude Code, with the plugin installed, open a copy of Acme as a project and ask:

- "weekly-status" or "monthly-status": a draft report from the registers.
- "mark T-1 done": the agent first asks for QA or test evidence (the definition of done) and changes nothing until you answer. Then it changes that one line, sets `done_on` to the date the work was finished, and renders the views.
- "finish the status report": Finish records the template version and the hashes, removes the template's comments and checks, and marks the document finished. With the `languages` block of section 6, it then asks once whether to translate the report now.
- "take the tasks from this chat export": the agent reads the export, shows the entries it proposes and writes nothing until you confirm. It never copies a password or token from the chat.

The agent never commits or pushes unless you ask. When you want a check before every commit, see "Check the registers in your own git hook" in the [README](../README.md).
